# Open MAIL A MONSTER in Roblox Studio

## Fastest route: open the built place

1. Download `build/MailAMonster.rbxlx` to your computer. Alternatively download
   `build/MailAMonster-source.zip` and unzip it; the place is in its `build` folder.
2. Install [Roblox Studio](https://create.roblox.com/) on Windows or macOS and sign
   in to your Roblox account.
3. In Studio choose **File → Open from File…** and select `MailAMonster.rbxlx`.
   Open the place itself; do not paste the source into the Command Bar.
4. Press **Play** (F5). The world, all eight islands, monsters, interface, and
   cosmetic models are generated by the game when the server starts. An empty
   scene before Play is expected.
5. Follow the tutorial: hatch, forward the NPC visitor, complete an activity,
   launch your Practice Voyage, then watch its homecoming and claim its reward.
   The practice voyage takes about 75 seconds.
6. Press **Stop** to end the test. The default backend is labeled **Studio
   simulation — progress is not saved**. Starting another session resets this
   local test. Persistent progress requires the live-service steps below.

No Rojo plugin, asset purchases, API key, Toolbox model, or paid product is needed
to open and try the supplied place. Optional audio is intentionally unconfigured;
all essential cues have visual equivalents.

## Publish a private test copy

1. Stop playtesting. Choose **File → Publish to Roblox**. If Studio already has
   the file associated with another experience, use **Publish to Roblox As…**
   and create a new experience rather than overwrite an unrelated one.
2. Name the experience **MAIL A MONSTER — Private Test**, select your own account
   or an appropriate creator group, select desktop and mobile devices, and click
   **Create**. Use a separate test experience, never an existing live game's data.
3. In [Creator Dashboard](https://create.roblox.com/dashboard/creations), open
   that experience, then **Configure → Settings** and confirm its **Audience**
   is **Private**. Do not change it to Public for these tests.
4. Open **Configure → Places**, select the starred start place, and set its
   **Maximum Player Count / Max Players** to **8** in its place settings.
   This platform setting is separate from the eight plots generated by code.
5. Open `ServerScriptService → MailAMonster → ServerConfig` in Studio's Explorer.
   Keep `LiveNamespace = "MAM_TEST_V1"` in this isolated test experience. Published
   Roblox servers always use real services; `Mode = "Simulation"` only enables
   the in-memory backend inside Studio.
6. To test real persistence from Studio too, set `Mode = "Live"`, then open
   **File → Experience Settings → Security** and enable **Enable Studio Access
   to API Services** for this test experience. Save/publish the configuration.
   The game uses Roblox server services directly; enabling HTTP Requests is
   unnecessary. No Open Cloud key needs to be pasted anywhere.
7. Launch the published test through Roblox. Rejoin and verify that monsters,
   Postage, cosmetics, tutorial progress, placements, and settings persist.
   See [TESTING.md](TESTING.md) for the two-server relay test and evidence to record.

Current Roblox audience rules make Private experiences accessible to the owner
and collaborators with **Edit** permissions. Playtest-only collaborators require
**Limited → Playtesters**, which has Roblox's Public/Limited eligibility
requirements. Use collaborators you trust; do not grant Edit merely to bypass
eligibility. The private two-server test can use authorized editor accounts.

## Publish publicly when you choose

Public release has not been performed by this project. Complete the Studio,
mobile, eight-player, and distinct live-server tests in [TESTING.md](TESTING.md)
first. For a launch, use a separate production experience or deliberately select
a new production data namespace after test data has been reviewed.

When you decide to release, publish the tested place, open its Creator Dashboard
**Configure → Settings → Audience**, choose **Public**, satisfy the eligibility
and **Maturity & Compliance** requirements shown for your selected audience, and
save. Roblox's age checks and additional all-ages requirements can change, so use
the live [official publishing requirements](https://create.roblox.com/docs/production/publishing/publish-games-and-places#publishing-requirements)
rather than assume owning a Roblox account is enough. The game contains no active
Robux purchase buttons or configured paid products.

## Edit source and rebuild

The complete source is in the repository and source ZIP. Install Python 3.10 or
newer. On Windows use `py -3` wherever these examples use `python3`.

```sh
python3 tools/setup.py
python3 tools/check.py
python3 tools/build.py
python3 tools/package.py
```

`setup.py` downloads **Rojo 7.7.1** and **Luau 0.698** into `.tools/bin`, verifies
the publisher's SHA256 hashes in `tools/versions.json`, and preserves TLS
verification. It supports Linux x86_64, Windows x86_64, and macOS x86_64/Apple
Silicon. The binaries and download cache are excluded from source control.
The initial download needs `github.com` and `release-assets.githubusercontent.com`.
Later checks and builds run without network access.

The pinned hashes come from the upstream release asset listings:
[Rojo](https://github.com/rojo-rbx/rojo/releases/expanded_assets/v7.7.1) and
[Luau](https://github.com/luau-lang/luau/releases/expanded_assets/0.698).
Never disable certificate or checksum checks to work around a download error.

Build output is `build/MailAMonster.rbxlx`. Reopen that file in Studio after each
build. Alternatively, install the official Rojo Studio plugin, run:

```sh
.tools/bin/rojo serve default.project.json
```

On Windows use `.tools\bin\rojo.exe serve default.project.json`. Connect the
plugin to `localhost:34872` and sync into a blank development place. The JSON
project maps shared modules, server scripts, client scripts, and remotes into
their correct Roblox services. Balance/content changes belong in
`src/shared/Config.lua` and `src/shared/Catalog.lua`; server backend settings
belong in `src/server/ServerConfig.lua`.

Use this task's existing checkout. Cloud tasks are already isolated; no Git
worktree is needed unless you explicitly want one. Stop a Rojo connection before
making temporary source edits directly in Studio, or syncing may replace them.

## What the cloud build proves

The cloud can run Luau compilation, deterministic service tests, and a genuine
Rojo place build. It cannot start Roblox Studio, render the scene, measure mobile
performance, or authenticate real players into two Roblox server jobs. Those
remaining checks are listed honestly in [TESTING.md](TESTING.md). Publishing to
Roblox is an action you perform from your own Studio account.
